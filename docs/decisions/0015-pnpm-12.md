# 0015. pnpm 12 adopted over 11.27.1

- Status: accepted
- Date: 2026-09-23

## Context and Problem Statement

The spec pinned pnpm 11.24.0 on 2026-08-27. pnpm 12.0.0 shipped the next day as a Rust rewrite; `latest` is now 12.5.1, while the 11 line still ships (11.27.1).

## Considered Options

- **Adopt 12.5.1.**
- **Hold 11.27.1** until CI and Docker images are rehearsed.
- **Hold 11** indefinitely.

## Decision Outcome

Chosen: **12.5.1**, after verifying it rather than trusting the release notes. All nine settings this spec relies on — `catalog:` with `catalogMode: strict`, settings living in `pnpm-workspace.yaml`, `allowBuilds`, `minimumReleaseAge` with its exclude, `forceLegacyDeploy`, `injectWorkspacePackages`, `peerDependencyRules.allowedVersions`, `blockExoticSubdeps`, isolated `node_modules` — behave as specified on 12.5.1, and a `turbo prune --docker` round-trip still passes a frozen install. The lockfile stays at version 9.0.

`forceLegacyDeploy: true` is **kept** although pnpm >= 12.2.0 no longer requires it, because `Dockerfile.api` calls `pnpm deploy --legacy` explicitly and one deploy mechanism is easier to reason about than two. Fallback if 12 causes trouble: 11.27.1, still maintained.

### Consequences

- Good: A much smaller install (3.9 MB against 20.5 MB) and faster resolution.
- Good: Unrecognised keys in `pnpm-workspace.yaml` are now a hard error, which catches typos in settings.
- Good: `turbo prune --docker` verified working with catalogs before Phase 4 depends on it.
- Bad: `allowBuilds` takes a mapping in pnpm 12, not a list; a list fails with a YAML parse error that reads like an unrelated problem.
- Bad: turbo must be >= 2.11.1, or `turbo gen` hits `ERR_PNPM_IGNORED_BUILDS`.
- Bad: CI images must not install pnpm with `--no-optional`: the binary ships through `@pnpm/exe.*` optional dependencies.
